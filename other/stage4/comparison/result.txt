Maven 3.9.9, Java 17.0.17, maven-dependency-plugin 3.11.0.
Для Maven использован отдельный, изначально пустой dev/stage4-maven-repository.
В UniPM: max_depth=10, фильтр отключён, load_order=true.

Maven взят из существующего кэша ~/.m2/wrapper/dists/apache-maven-3.9.9-bin/.
Команды из корня проекта, Git Bash; для них Maven должен быть в PATH:

При повторе Maven использует кэш. Для нового наблюдения скачиваний нужно указать другой пустой каталог maven.repo.local.

Состав и версии совпали: корневой пакет и три зависимости. UniPM сохраняет общее ребро platform-commons -> apiguardian; Maven помечает повторное включение как omitted for duplicate. В списке UniPM apiguardian также встречается один раз.

Порядок различается по смыслу. UniPM вычисляет порядок «зависимость раньше зависимого»: apiguardian идёт перед platform-commons, корень — последним. dependency:resolve показывает порядок classpath. Фактические скачивания Maven не следуют топологическому порядку: запросы пересекаются, поэтому порядок завершения отличается от порядка начала. Кэш при повторном запуске устраняет уже выполненные скачивания. POM и артефакты самого Maven-плагина в приведённые списки JAR пакета не включены.

Оба запуска завершились успешно. Maven используется только для сравнения; UniPM не вызывает его и не использует его библиотеки. Результат относится к этому примеру: parent, BOM и dependencyManagement по-прежнему не поддерживаются UniPM.

Описание порядка dependency:resolve: https://maven.apache.org/plugins/maven-dependency-plugin/resolve-mojo.html#sort
Стадии работы Maven Resolver: https://maven.apache.org/resolver/how-resolver-works.html
